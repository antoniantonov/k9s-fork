## Executive summary

This repository is a Go terminal application. K9s uses the
`github.com/derailed/tview` widget toolkit on top of
`github.com/derailed/tcell/v2` for terminal drawing and keyboard input. Kubernetes
resources are watched through `client-go`, transformed by DAO/model layers, and
rendered into tview tables, trees, text views, dialogs, and custom charts.

The repository already lists NetworkPolicy objects in a table and already has an
XRay tree facility, but it does not calculate effective NetworkPolicy
reachability. The best implementation is a new native Go view, tentatively named
`netpolgraph`, rendered with `tview.Flex`. The view has independently toggleable
ingress and egress panels, rule and primitive display modes, keyboard selection,
per-item separators, and a bottom details panel. Primitive mode supports CIDRs,
Pods, Namespaces, Deployments, and Jobs, with green/red effective-access
coloring.

```text
Subject: Deployment default/api (3 pods)   Ingress: ON   Egress: ON
┌ INGRESS [PRIMITIVES] ─────────────────┬ EGRESS [RULES] ──────────────────────┐
│ [green] Deployment web                │ allow-database / egress rule 0       │
│ ───────────────────────────────────── │ ──────────────────────────────────── │
│ [red]   Namespace untrusted           │ allow-dns / egress rule 1            │
└───────────────────────────────────────┴───────────────────────────────────────┘
┌ DETAILS ──────────────────────────────────────────────────────────────────────┐
│ Selected: Deployment web; effective ingress: allowed; evidence: allow-web... │
└───────────────────────────────────────────────────────────────────────────────┘
```

## 4. Current NetworkPolicy support

K9s already knows the standard NetworkPolicy GVR:

```go
networking.k8s.io/v1/networkpolicies
```

at `internal/client/gvrs.go:39`.

`internal/model/registry.go:157-160` registers `render.NetworkPolicy`, and
`internal/render/np.go` produces a normal table with:

- selected pod selector;
- ingress selectors, ports, and IP blocks;
- egress selectors, ports, and IP blocks;
- labels, validity, and age.

The helper functions flatten rules into strings. They do not:

- identify the pods selected by each policy;
- combine multiple policies additively;
- calculate ingress and egress isolation;
- evaluate both ends of a connection;
- resolve workload selections to pods;
- calculate effective pod-to-pod reachability;
- render a relationship diagram.

Current XRay support is also insufficient by itself:

- `internal/view/command.go:89-99` allows XRay only for pod, service,
  deployment, daemon set, stateful set, and replica set.
- NetworkPolicy has no XRay `TreeRenderer`.
- Jobs and namespaces are not accepted as XRay roots.
- XRay represents ownership/reference relationships, not bidirectional policy
  decisions.

## 5. Planned feature: NetworkPolicy reachability view

### Goals

From a selected Pod, Deployment, Job, or Namespace, show:

1. Which in-cluster workloads/pods or external CIDRs can establish ingress
   connections to the subject.
2. Which in-cluster workloads/pods or external CIDRs the subject can reach via
   egress.
3. Which policies and rules caused each result.
4. Whether access is unrestricted, restricted to ports, denied, or uncertain.
5. Live updates when pods, labels, namespaces, or NetworkPolicies change.

### Non-goals for the first version

- Proving actual packet delivery through CNI implementation details.
- Modeling service meshes, application authorization, cloud firewalls, node
  firewalls, DNS resolution, NAT, routes, or load balancers.
- Modeling vendor-specific policy CRDs such as CiliumNetworkPolicy,
  Calico GlobalNetworkPolicy, or AdminNetworkPolicy.
- Inferring live traffic from flow logs.

The UI must label its result as **Kubernetes NetworkPolicy reachability**, not
guaranteed end-to-end connectivity.

### Command and contextual action

Recommended command:

```text
:netpolgraph <kind> <name> [namespace]
```

Aliases:

```text
:npg
:npgraph
```

Examples:

```text
:npg pod api-7d8c9f default
:npg deployment api default
:npg job database-migration default
:npg namespace payments
```

Do not reuse `:np`; it already resolves to the standard NetworkPolicy resource
table.

The best UX also adds one contextual key action to Pod, Deployment, Job, and
Namespace tables. `Shift-N` is an illustrative choice and must be checked
against each view's active bindings before implementation:

```text
Shift-N  Network Reachability
```

The contextual action passes the current GVR and selected fully qualified name
directly to the new view. This avoids making users retype a selected resource.

### Rule and primitive modes

Each direction panel has an independent display mode:

- **Rules mode:** list the NetworkPolicy rules that affect the subject in that
  direction.
- **Primitives mode:** list candidate CIDRs and cluster primitives and show
  whether their effective connection to/from the subject is allowed.

Controls:

- `m`: toggle Rules/Primitives for the focused direction panel.
- `M`: set both visible direction panels to the focused panel's mode.
- Mode changes preserve each mode's last selected item and scroll position.

Rules mode must include:

- explicit NetworkPolicy rules from every policy selecting at least one subject
  pod;
- policy namespace/name, direction, and stable zero-based rule index;
- peer selector or CIDR summary;
- ports/protocol summary;
- number of subject pods selected by the policy;
- synthetic `Unrestricted (no isolating policy)` and
  `Default deny (isolated, no matching allow rule)` entries where needed.

NetworkPolicy has allow rules, not explicit deny rules. A disallowed result must
be explained as isolation plus the absence of a matching allow rule, rather than
claiming that a deny rule exists.

Primitives mode supports these independently toggleable kinds:

- CIDRs;
- Pods;
- Namespaces;
- Deployments;
- Jobs.

Pods owned by StatefulSets, DaemonSets, ReplicaSets without a resolvable
Deployment, or other unsupported owners still appear as Pod primitives. They do
not receive an additional workload aggregate row in the first implementation.

Pressing `f` opens a small multi-select filter dialog for the focused direction.
The dialog uses checkboxes for the five kinds, `Enter` to apply, and `Esc` to
cancel. Filter state is independent for ingress and egress. At least one kind
does not need to remain enabled; an empty selection displays
`No primitive kinds selected`.

CIDRs are obtained from NetworkPolicy `ipBlock` peers. They are not discoverable
cluster objects, so the view can only list CIDRs expressed by relevant policies,
plus a synthetic all-address range when policy semantics explicitly require it.

### Primitive access coloring and aggregate rules

Primitive rows use background color:

- **Green:** the primitive is fully allowed in the displayed direction.
- **Red:** the primitive is not fully allowed.

Use readable foreground colors from the active skin. Add dedicated configurable
colors if existing table colors do not provide enough contrast.

Pods and CIDRs can normally be evaluated directly. Namespaces, Deployments, and
Jobs contain or represent multiple pods, so use a conservative aggregate:

- green only when all relevant member-pod connection pairs are allowed;
- red when no pairs are allowed;
- red with an explicit `[PARTIAL allowed/total]` label when only some pairs are
  allowed;
- red with `[EMPTY]` when a workload currently has no pods and therefore cannot
  be proven reachable.

This keeps the requested green/red model while avoiding a misleading green row
for a partially reachable workload. The details panel must expose exact pod-pair
counts and per-port differences.

For ingress, the primitive is the source and the subject is the destination.
For egress, the subject is the source and the primitive is the destination.
Effective color therefore always includes policy evaluation at both endpoints.

### Bottom details panel

The bottom panel updates immediately whenever selection changes. It is
scrollable and has two layouts based on the selected item type.

For a selected primitive, show:

| Field | Content |
|---|---|
| Direction | Ingress or egress |
| Primitive | Kind, namespace/name, UID when applicable |
| Subject | Kind, namespace/name, selected pod count |
| Effective access | Allowed, disallowed, partial, unknown, or partial-data |
| Coverage | Allowed pod pairs / total evaluated pod pairs |
| Ports | All ports or normalized protocol/port/range list |
| Allow evidence | Policies and rule indexes that contribute allowed traffic |
| Disallow explanation | Isolated side and why no allow rule matched |
| Warnings | RBAC gaps, unresolved named ports, unsupported CNI semantics |

The disallow explanation should use wording such as:

```text
Disallowed: destination pod default/api-123 is ingress-isolated and no ingress
rule selects source pod untrusted/client-456 on TCP/443.
```

For a selected rule, show:

- policy namespace/name and UID;
- direction and rule index;
- policy pod selector and number of subject pods selected;
- peer entries with pod selector, namespace selector, or IP block;
- ports, protocols, named ports, and ranges;
- YAML-like rule summary;
- warnings or unsupported semantics;
- an applicability table below the rule details.

The rule applicability table lists all currently enabled primitive kinds to
which the selected rule could apply:

| Primitive | Type | Peer matches | Opposite side allows | Effective | Ports |
|---|---|---:|---:|---:|---|
| `web/frontend` | Deployment | yes | yes | green | TCP/443 |
| `untrusted` | Namespace | yes | no | red | none |
| `10.0.0.0/8` | CIDR | yes | n/a | green | TCP/443 |

For ingress rules, `Peer matches` means the primitive matches the rule's `from`
peer. `Opposite side allows` means source egress permits the connection. For
egress rules, `Peer matches` means the primitive matches the rule's `to` peer,
and `Opposite side allows` means destination ingress permits it.

A peer match alone is not enough to color the row green; effective access must
pass both sides of NetworkPolicy evaluation.

The applicability table uses the same conservative aggregate and green/red
coloring as primitive mode. It respects the focused direction's primitive-kind
filter so users can control table size.

### Subject resolution

Normalize every selected primitive into a `Subject` containing one or more pods:

```go
type Subject struct {
    Kind      SubjectKind
    Namespace string
    Name      string
    Pods      []PodRef
}
```

Resolution rules:

- **Pod:** exactly the selected pod.
- **Deployment:** current pods controlled by its ReplicaSets. The existing
  selector path in `internal/view/dp.go:49-94` is reusable, but owner UID checks
  should be preferred where possible so unrelated pods with matching labels are
  not included.
- **Job:** current pods owned by the Job. `internal/view/job.go:27-56` already
  resolves Job-to-Pod navigation from `job.Spec.Selector`; owner UID checks are
  again safer.
- **Namespace:** all pods currently in the namespace. Results are aggregated,
  with drill-down to individual pods because different pods can have different
  policies.

Empty controllers and completed Jobs are valid subjects. The view should say
that no current pods exist and optionally evaluate the pod template as a
separate future enhancement; it must not silently invent live reachability.

### Data required

The evaluator needs a consistent snapshot of:

- Pods across all namespaces.
- Namespaces and their labels.
- `networking.k8s.io/v1` NetworkPolicies across all namespaces.
- Deployments, ReplicaSets, and Jobs across all namespaces so primitive mode can
  list them and resolve workload ownership accurately.
- The selected subject object.

Cluster-wide list/watch permissions are necessary for a complete graph. If RBAC
allows only some namespaces, render a prominent **partial data** warning and
list which resource requests failed. Do not present partial results as complete.

### Correct Kubernetes NetworkPolicy semantics

NetworkPolicy is additive. There is no rule ordering and one policy cannot
subtract traffic allowed by another standard NetworkPolicy.

For each pod and direction:

1. Find all NetworkPolicies in the pod's namespace whose `podSelector` selects
   that pod.
2. Determine whether those policies isolate the pod for ingress and/or egress
   according to `policyTypes` and API-defaulted behavior.
3. If the pod is not isolated in a direction, that direction is unrestricted by
   standard NetworkPolicy.
4. If isolated, union all traffic allowed by all selecting policies in that
   direction.

For a candidate connection `source -> destination`, effective standard policy
permission is:

```text
(source egress is unrestricted OR a source egress rule allows destination)
AND
(destination ingress is unrestricted OR a destination ingress rule allows source)
```

Both sides matter. Showing only policies attached to the selected pod would
produce incorrect reachability.

Peer matching must implement:

- `podSelector` alone: matching pods in the policy's own namespace;
- `namespaceSelector` alone: all pods in matching namespaces;
- both selectors in one peer: intersection of matching namespaces and pods;
- empty selectors: match-all according to Kubernetes semantics;
- `ipBlock.cidr` and `except`: external/CIDR nodes;
- an empty `from` or `to` list in a rule: all sources or destinations;
- an empty `ports` list: all ports/protocols;
- protocol, numeric port, named port, and `endPort`.

The matcher must distinguish absent selectors from present-but-empty selectors.
For example, `namespaceSelector: {}` matches all namespaces, while an absent
`namespaceSelector` combined with a pod selector keeps pod matching in the
policy's namespace. Likewise, `podSelector: {}` matches all pods in its resolved
namespace scope, while an absent pod selector does not mean the same thing.

YAML indentation matters because two peer entries are a union while a single
peer containing both namespace and pod selectors is an intersection. The
evaluator should work from typed API objects and never from the flattened
strings in `internal/render/np.go`.

### Ports and edge representation

Reachability without a requested port is not a simple boolean. An edge may allow
all ports or only a subset. Represent permissions explicitly:

```go
type Edge struct {
    Source      EndpointRef
    Destination EndpointRef
    Permissions []PortPermission
    Evidence    []PolicyEvidence
    State       EdgeState
}
```

`PortPermission` should support protocol, number, name, and range. Resolve named
ports against destination pod container ports when the semantics and available
objects permit it. Egress named-port behavior has historically varied across
implementations, so ambiguous or CNI-dependent cases should be `Unknown` rather
than optimistically allowed. If heterogeneous pods resolve the same name
differently, retain per-pod results and mark the aggregate as partial.

### Aggregation

Pod-level evaluation is the source of truth. Workload and namespace rows are
presentation aggregates.

For a multi-pod subject:

- **All:** peer can reach every subject pod, or every subject pod can reach peer.
- **Some:** only a subset is reachable; show `2/3 pods`, mark the result partial,
  and use the conservative red primitive background.
- **None:** no effective edge.

Peer pods can initially be grouped by:

1. namespace;
2. top-level owner workload when owner references can be resolved;
3. individual pod when no stable owner exists.

The user must be able to expand aggregates to avoid hiding asymmetric policy
behavior.

### Unlimited candidate sets

An unrestricted direction cannot be usefully expanded into every pod by
default. Render a synthetic node such as:

```text
∞ All cluster pods (subject to the opposite endpoint's policy)
```

Then allow expansion or filtering. External all-address access should be shown
separately and only when it follows from an `ipBlock` or an unbounded peer; do
not assume all Internet traffic can route to a pod.

## 6. Implementation plan for a coding agent

### Implementation constraints

The implementation agent should follow these constraints:

- Keep NetworkPolicy evaluation independent from terminal rendering.
- Use typed Kubernetes API objects; do not parse strings produced by
  `internal/render/np.go`.
- Reuse the existing `watch.Factory`, `App.inject`, `ui.KeyActions`, styles, and
  component lifecycle.
- Keep UI state such as panel visibility, mode, filters, selection, and scroll
  position separate from evaluator state.
- Preserve errors and partial-data warnings; do not silently return an empty
  successful graph.
- Use stable IDs for rules and primitives so refreshes do not reset selection.
- Add targeted unit tests before wiring the complete view.
- Do not alter the existing `:np` NetworkPolicy table command.

### Evaluator API

Expose an API that can evaluate both display modes without duplicating policy
logic:

```go
type Evaluator interface {
    EvaluateSubject(context.Context, SubjectRef, Snapshot) (SubjectResult, error)
    Rules(SubjectResult, Direction) []RuleResult
    Primitives(SubjectResult, Direction, sets.Set[PrimitiveKind]) []PrimitiveResult
    RuleApplicability(
        SubjectResult,
        RuleID,
        sets.Set[PrimitiveKind],

```

`SubjectResult` should retain pod-level decisions so that rules, primitives, and
details are projections of the same evaluated data. `RuleApplicability` must not
reimplement reachability with weaker semantics.

Create a dedicated model:


- call the pure evaluator;

### Why not implement it as an XRay renderer?

Reusing `ui.Tree` is possible for a minimal first prototype, but extending XRay
directly is not ideal:

- reachability is directed and many-to-many;
- one selected subject needs inbound and outbound perspectives;
- effective permission depends on both endpoints;
- ports and policy evidence belong to edges, not only nodes;
- a namespace or workload can have mixed per-pod results.

The evaluator should be independent of rendering. A tree renderer can then be an
optional compact mode, while the planned Flex view presents the requested
rule/primitive interaction more accurately.

### Performance

A naive all-pod-pairs calculation is `O(P²)` and will be expensive on large
clusters. Use:

- namespace and label indexes;
- precompiled `labels.Selector` values;
- policy-to-selected-pod indexes;
- cached owner/workload resolution;
- candidate generation from policy peers instead of blind Cartesian products;
- incremental/debounced recomputation after watch events;
- a configurable display/result cap with an explicit truncation warning.

For v1, correctness is more important than premature incremental complexity. A
snapshot evaluator with indexes and a short debounce is a reasonable starting
point.

### Error and uncertainty handling

The view should distinguish:

- **Denied:** enough data exists and standard policy semantics deny the edge.
- **Allowed:** enough data exists and standard policy semantics allow at least
  the displayed ports.
- **Partial:** RBAC or list/watch failures make the answer incomplete.
- **Unknown:** a feature cannot be resolved, such as an ambiguous named port or
  unsupported policy type.
- **Out of scope:** CNI-specific or non-NetworkPolicy controls may change actual
  traffic.

Other important caveats:

- NetworkPolicy enforcement depends on the cluster's network plugin.
- Existing connections may behave differently during policy changes depending
  on the implementation.
- `hostNetwork` pods and node-local traffic can be CNI-specific.
- `ipBlock` behavior can differ before or after address translation.
- Pods on networks not governed by the standard policy implementation must be
  marked unsupported/uncertain.

### Testing strategy

#### Pure evaluator tests

Use table-driven typed Kubernetes objects for:

- no policies: ingress and egress unrestricted;
- default-deny ingress;
- default-deny egress;

- watch/list refresh produces graph updates;
- rapid events are debounced;
- cancellation stops updates;

## 7. Recommended implementation decision

Implement `:netpolgraph`/`:npg` as a native Go tview/tcell component backed by a
pure `internal/netpol` evaluator. Start with pod-level correctness, especially
two-sided additive policy and port semantics, then aggregate those verified
results for Deployments, Jobs, and Namespaces.

The initial view should use a root vertical Flex, independently removable
ingress and egress panels, independent Rules/Primitives modes, five primitive
kind filters, separator-delimited selectable items, and a persistent details
area. Reuse K9s's component lifecycle, watchers, actions, styles, tables, Flex
layouts, and navigation conventions. Do not build the feature by parsing the
existing NetworkPolicy table strings.
